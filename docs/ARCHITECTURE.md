# Architecture — AI Worker Platform

## Overview

The platform wraps the existing Bash automation engine with a Nuxt 3 management application and PostgreSQL. The worker remains a separate process (Docker service or host systemd) and never runs inside the Nuxt event loop.

```text
┌─────────────┐     HTTPS/HTTP      ┌──────────────────┐
│  Browser UI │ ──────────────────► │  web (Nuxt 3)    │
└─────────────┘                     │  /api/v1/*       │
                                    └────────┬─────────┘
                                             │ SQL
                                             ▼
                                    ┌──────────────────┐
                                    │  PostgreSQL      │
                                    │  (private net)   │
                                    └────────▲─────────┘
                                             │ heartbeats,
                                             │ control_requests,
                                             │ task_runs
                                    ┌────────┴─────────┐
                                    │  worker          │
                                    │  worker.sh +     │
                                    │  platform wrapper│
                                    └────────┬─────────┘
                                             │
                         conf export / logs / workspaces
                                             │
                                    ┌────────▼─────────┐
                                    │  Persistent vols │
                                    │  config, state,  │
                                    │  logs, workspace │
                                    └──────────────────┘
```

## Process boundaries

| Service | Responsibility | Must not |
|---------|----------------|----------|
| **web** | Auth, UI, CRUD APIs, config export trigger, audit, log SSE | Run AI agents; accept arbitrary shell; mount Docker socket |
| **worker** | Poll forges, run Bash runners, hold locks, heartbeat, ack control requests | Expose public ports; write authoritative settings except status |
| **db** | Persist users, repos, settings, runs, sessions, audit | Be published publicly |

## Configuration synchronization

1. Operator changes repositories/settings in the UI → validated → PostgreSQL transaction + audit log.
2. Config sync service writes temp JSON files, validates with `jq`, atomically renames into:
   - `$AI_WORKER_BASE_DIR/github-projects.conf`
   - `$AI_WORKER_BASE_DIR/gitlab-projects.conf`
3. A `config_version` setting increments; worker records the version it loaded.
4. Active AI runs are **not** interrupted by settings changes. Changes apply to future tasks.
5. Only the web/config-sync path writes conf files. Worker is read-only for conf.

Trade-off: temporary dual representation (DB + files). Chosen because it preserves the battle-tested Bash parser with minimal risk versus rewriting conf loading in SQL.

## Worker control IPC

Table `control_requests`: `{ id, action, status, requested_by, payload, created_at, acknowledged_at, completed_at, result }`.

Allowed actions: `reload_config`, `start`, `stop`, `restart`.

Webhook wake uses a shared-volume wake file (not a control action) so idle sleep can interrupt within a few seconds without bouncing the worker process.

### Multi-worker repo claims

Before flipping forge labels (`ai` → `ai-working`, `ai-review` → `ai-reviewing`), a job calls `POST /api/v1/worker/internal/claim-repo` which takes a short Postgres lease (`worker_repo_claims`, default **10s** via `REPO_CLAIM_TTL_SECONDS`). Only one worker wins; others skip that repo. After labels flip, forge state is the durable lock. Local `flock` still prevents duplicates on a single host.

Worker wrapper polls pending requests, validates action allowlist, acknowledges, performs safe operation, writes result. Stop/restart wait for idle agents when `graceful` is true (default).

## Task history

Runners continue writing filesystem logs/results. A small platform hook / watcher records `task_runs` rows with `log_path` relative to the logs volume. SSE streams append-only content from that path after authz checks — never arbitrary paths.

## Authentication

- Credentials: Argon2id password hashes in `users`
- Sessions: durable store in PostgreSQL; HttpOnly, SameSite=Lax (Strict where compatible), Secure in production
- CSRF: double-submit or Nuxt/h3 CSRF token on mutating routes
- Roles: `admin`, `operator` (read-mostly + limited actions)
- First-run: bootstrap creates one admin when no users exist; requires a strong `INITIAL_ADMIN_BOOTSTRAP_SECRET` from `scripts/generate-env.sh` (no default) plus interactive `/setup` (or `INITIAL_ADMIN_USERNAME`) when the users table is empty
- Required app secrets are generated by `scripts/generate-env.sh`, validated at container entrypoint + Nitro startup, and persisted to `/data/config/app-secrets.env` so the host `.env` can be removed after first boot

### Path variables inside the worker

- `WORKER_CODE_DIR` — scripts, `lib/`, `prompts/` seed files (directory of the executing script).
- `BASE_DIR` / `AI_WORKER_BASE_DIR` — runtime data: conf files, `logs/`, `state/`, `.env`.

### Prompt templates (DB-backed)

`worker/prompts/` files are **seeders**. On web startup, `ensurePromptRows()` inserts missing rows into `prompt_templates` (never overwrites UI edits). Admins edit content on the **Prompts** UI page. Before each job, `ai_prompt_render` fetches live content from `GET /api/v1/worker/internal/prompts` into `$BASE_DIR/state/prompts-live/` (falls back to seed files if the API is unavailable).

## Filesystem layout (runtime)

```text
/data/
  config/          # exported conf, .env for worker (secrets via env preferred)
  state/           # locks, running markers
  logs/            # worker + per-task logs
  workspaces/      # managed clones (repo UUID directories)
```

## Forge connections and persistent workspaces

The product uses an **administrator-managed shared connection model** (same trust boundary as existing shared repositories). Operators can view; admins connect/disconnect and register repos.

```text
UI Connections → OAuth (PKCE) → forge_connections (encrypted tokens)
                 → discovery sync → discovered_repositories
                 → auto-register all (enabled, workspace not_cloned)
                 → 15‑min discovery sync (+ manual Fetch new repos)
                 → lazy clone on first AI job → workspace_operations
                 → async clone/sync into WORKSPACE_ROOT/<workspaceId>
                 → exportWorkerConfig + forge-credentials.env
                 → Bash worker polls labels using path + GH_TOKEN/GITLAB_TOKEN
                 → Optional forge webhooks (label ai / ai-review) wake the poll loop early
                 → Before label mutations: POST /api/v1/worker/internal/ensure-labels
                   (creates any missing AI_* labels on the forge project at runtime)
```

### Runtime forge labels

`AI_WORKER_LABELS` (server) is the source of truth. Labels are ensured:

1. When a repository is registered or enabled
2. During connection discovery / refresh (backfill all projects)
3. Before the worker changes issue/PR labels (`ensure-labels` internal API, with local `gh` / GitLab fallback)

So existing projects automatically receive new labels (for example `no-change`, `ai-answered`) the next time the worker touches that repo — no rebuild or manual setup required.

### Forge webhooks (optional, faster pickup)

Polling remains the source of truth. When configured, GitHub/GitLab call:

- `POST /api/v1/webhooks/github/:connectionId`
- `POST /api/v1/webhooks/gitlab/:connectionId`

Verified with per-connection secrets (GitHub HMAC / GitLab token). On `ai` or `ai-review` label add, the API writes `$AI_WORKER_BASE_DIR/state/wake-poll` so `worker.sh` breaks out of its sleep and polls immediately. Use **Setup webhooks** on a connection (or per repository). `APP_BASE_URL` must be reachable from the forge.


| Table | Role |
|-------|------|
| `forge_connections` | Provider account, instance URL, encrypted access/refresh tokens, sync status |
| `oauth_states` | Short-lived OAuth CSRF state + PKCE verifier |
| `discovered_repositories` | Cached provider catalog (not every page hit) |
| `repositories` | Registered automation targets (+ workspace status, provider identity) |
| `workspace_operations` | Queued clone/sync/verify/delete jobs |

### Workspace rules

- One deterministic directory per `workspace_id` under `WORKSPACE_ROOT`
- Paths validated against escape; clone/fetch use `execFile` argument arrays
- Routine sync fetches and fast-forwards only when the tree is clean — never `git reset --hard`
- Concurrent ops on the same repo are serialized; tokens stripped from stored remotes and logs
- Worker continues to consume `{ name, path, block_on_open_pr }` conf; DB remains source of truth

### Credential path to the worker

1. Tokens encrypted in PostgreSQL with `SECRET_ENCRYPTION_KEY` (AES-256-GCM).
2. On forge connect/disconnect/refresh, web writes `/data/config/forge-credentials.env` (0600).
3. On AI provider connect/disconnect (Providers UI) — or from compose `.env` `CURSOR_API_KEY` / `ANTHROPIC_API_KEY` / `CLAUDE_CODE_OAUTH_TOKEN` / `OPENAI_API_KEY` / `CODEX_API_KEY` / `GEMINI_API_KEY` / `COPILOT_GITHUB_TOKEN` — web writes `/data/config/provider-credentials.env` (0600). DB-stored secrets override env when both are set.
4. `scripts/worker-entrypoint.sh` sources that file before `platform-wrapper.sh`.
5. Project conf JSON never contains tokens.
6. **AI agent phase** runs under `lib/ai-isolation.sh`: forge tokens, app secrets, git credential helpers, and SSH keys are withheld from the agent; only the trusted runner (validate/publish) uses forge credentials afterward. See `docs/SECURITY.md`.

### SSRF policy for GitLab URLs

User-supplied GitLab instance URLs are normalized, require HTTPS by default, block localhost/metadata/private ranges unless listed in `GITLAB_TRUSTED_HOSTS`, resolve DNS before fetch, and refuse redirects that leave the approved origin.

## Security boundaries

- No Docker socket in any service
- No privileged containers
- PostgreSQL only on internal compose network
- Web binds `127.0.0.1:8080` by default
- Path validation for workspaces; reject `..`, odd URL schemes, embedded credentials
- Logs escaped as text in UI; never executed
- Secrets encrypted at rest; never returned by API
- OAuth tokens never returned to browser clients after connection
- GitLab instance URL SSRF protections (see above)
- AI agent process isolated from forge publishing credentials (env scrub + bubblewrap overlays); orchestration performs git/PR/MR/comment writes

See `docs/SECURITY.md` for the operational checklist.
