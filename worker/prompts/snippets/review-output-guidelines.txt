Structure the Markdown review like this:

## Summary
Brief overall assessment of THIS change only (what the diff does and whether it looks ready). Do not summarize or judge the rest of the project.

## Issue / task alignment
If linked issues were provided: for each issue, say whether the PR/MR addresses it (fully / partially / not at all), with concrete evidence from the diff. If no linked issues, write "No linked issues referenced."

## Responses to discussion
Required when developers commented after a prior AI review: answer each recent developer comment directly (acknowledge, reasoning, impact on verdict). Required when maintainers commented: confirm how you applied their override (e.g. dropped CI/CD findings).

## Changes since previous AI review
Required when a prior automated AI review appears in the thread: what you dropped from the previous review, what still applies, what's new.

## Strengths
What looks good.

## Issues
Ordered by severity (blocker / major / minor / nit).
For each issue include:
- file path and approximate location when possible
- what is wrong
- why it matters
- a concrete suggestion
Include unmet acceptance criteria from linked issues as findings when applicable.

## Testing
Required. This section is how a reviewer sees whether the change was tested. Do not skip it and do not audit tests or coverage of unchanged code.
Write each of these, with file paths from the diff:
- Test files in this diff, or "none"
- What those tests assert about the changed behavior, and which branches or error paths in the diff they miss
- Commands you ran and the results, or why they could not run
- Coverage of changed executable lines: tool, command, and percent, or "not measured" and why
Changed executable lines must be above 80% covered. If tests are missing, weak, failing, or that coverage is 80% or below, list it as a major issue unless the diff has no executable logic.

## Verdict
One of: Approve / Request changes / Needs discussion — with one short sentence why.
If linked issues are only partially met, prefer Request changes unless the gap is clearly out of scope.
If executable code changed and the tests for it are missing, weak, failing, or not above 80% coverage of the changed lines, use Request changes.

Be specific and technical. Prefer fewer high-signal findings over vague advice.
If the diff is truncated, say so and review only the visible hunks.

Every bullet in Strengths, Issues, and Testing must point at a changed
file/hunk from the PR/MR diff. Do not discuss unrelated modules,
pre-existing code, or the rest of the project.

Do not flag style, formatting, or "make this prettier" issues on unchanged
or unrelated code. Do not recommend drive-by refactors, extra files, or
reformatting of existing classes. If the diff touches files or classes
that the issue did not require, call that out as scope creep.
Focus on correctness, requirements, bugs, and risk in the actual diff.
